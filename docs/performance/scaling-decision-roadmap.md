# Evidence-Based Scaling Decision Roadmap

Cambium remains a clean modular monolith while single-node capacity satisfies real demand. Each scaling step below requires **documented metric evidence** before adoption.

| Proposal | 1. Bottleneck | 2. Evidence Required | 3. Current Workaround | 4. Proposed Change | 5. Complexity | 6. Cost Impact | 7. Ops Burden | 8. Failure Modes | 9. Migration Strategy | 10. Trigger Condition |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Upgrade Render Instance** | Node CPU/RAM ceiling | Sustained RSS > 80% or event-loop lag p95 > 100ms | Payload caps (`2mb`, `limit<=100`), L1 cache bounds | Vertical upgrade (`Starter -> Standard 2GB`) | Low | Higher fixed monthly compute | Minimal | OOM kills under PDF OCR bursts | Blueprint update in `render.yaml` | Sustained RAM > 80% for 1h during peak |
| **Enable PgBouncer Pooling** | PG `max_connections` saturation | `activeConnections/maxConnections >= 0.85` on telemetry | `DB_POOL_MAX=20` per instance | Point `POSTGRES_PGBOUNCER_PORT` to Supabase/Render pooler | Low | Included / low | Low | Prepared stmt incompatibilities in transaction mode | Env var switch in `database.config.ts` | Multiple API replicas or > 60% PG connection utilization |
| **Activate Managed Redis (`REDIS_URL`)** | Split-brain L1 rate-limit/cache across >1 API node | Multi-replica deploy + inconsistent rate limits / high cache miss | L1 LRU map + PG durable queue | Provision single Redis instance shared by API nodes | Medium | Managed Redis tier | Medium | Redis disconnect (already auto-falls back to L1/PG!) | Set `REDIS_URL` env; zero code rewrite | Horizontal scaling to `>= 2` API instances |
| **Dedicated Background Worker** | Heavy OCR / ingestion spikes delaying HTTP API | Event-loop p95 > 150ms during batch ingestion | In-process worker pool capped at `3` | Boot `QueueService` consumer in separate Render worker service | Medium | Extra worker instance | Medium | Queue stall if worker crashes | Disable HTTP listener on worker entrypoint | Sustained ingestion/OCR volume interfering with interactive `p95` |
| **PostgreSQL Read Replica** | Analytics/catalog queries contending with writes | DB slow queries (`>1s`) correlated with dashboard reports | `idx_opps_fts` GIN + `004` composite indexes + L1 cache | Set `POSTGRES_REPLICA_HOST` in `database.config.ts` | Medium | ~2x DB compute | Medium | Replication lag (`100ms–2s`) on read-after-write | Already wired in `getDatabaseConfig()` | Read CPU > 70% after index & cache tuning |
| **Dedicated Search (OpenSearch) / Microservices** | Billion-row sharding / specialized search | `pgvector` HNSW + GIN FTS `p95 > 500ms` after tuning | `pgvector` HNSW + PostgreSQL `idx_opps_fts` | **Defer** until PG exceeds tens of millions of documents | High | Significant infra & sync cost | High | Index drift vs DB source of truth | Dual-write outbox CDC relay | Verified PG index saturation well beyond 1M+ corpus rows |
