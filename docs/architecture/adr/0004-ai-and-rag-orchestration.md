# ADR 0004: AI Intelligence & Retrieval-Augmented Generation (RAG) Architecture

## 1. Context & Problem Statement
Cambium Research powers deep scholarship intelligence:
1. **Agentic Manuscript Reader (`/agent-reader`)**: Providing 3 specialized reviewer personas (*Methodology Auditor*, *Statistical Rigor*, *Reproducibility Engine*).
2. **Grant Opportunity Matching**: Computing mathematical semantic affinity (0–100%) between scholar research trajectories and global funding RFPs.
3. **Academic Citation Integrity**: Every claim generated by the platform must be strictly grounded to exact source text, page numbers, and line numbers (`[p. 14, L. 42–58]`). Hallucinated claims or citations destroy scholarly trust.

We must choose between **direct in-engine deterministic RAG orchestration** versus **heavyweight autonomous multi-agent frameworks** (e.g. LangChain, LangGraph, CrewAI, AutoGPT).

---

## 2. Decision Drivers
- **Zero Hallucination Mandate**: The AI must produce traceable citations with verifiable source provenance; unverifiable assertions must be rejected.
- **Deterministic Latency & Cost Predictability**: Autonomous open-ended loops risk unbounded API token burn and unpredictable timeouts.
- **Offline / CI Resilience**: The system must run automated test suites (`npm run test:jest`, `vitest`) without requiring live external API keys or incurring costs.
- **Lean Architecture**: Minimizing third-party library churn and breaking changes in fast-moving AI wrapper ecosystems.

---

## 3. Options Considered
1. **Direct In-Engine Deterministic RAG (Google Gemini + Fallback)** *(Selected)*
2. **Heavyweight Agentic Framework (LangGraph / CrewAI)**
3. **LlamaIndex Enterprise Pipeline**
4. **Pure Keyword Retrieval (BM25 Only)**

## 5. Decision & Rationale
We selected **Direct In-Engine Deterministic RAG** orchestrated in NestJS using **Google Gemini models** (`gemini-embedding-001` for 768-dim vectors; Gemini 1.5 Pro / Flash for synthesis) backed by a **deterministic mathematical fallback engine**.

### Rationale:
- **Strict Provenance Verification**: In [`server/src/modules/reader/document-parser.service.ts`](file:///d:/01_PROJECTS/ACTIVE/S92_Imthiyas_Capstone_Cambium/server/src/modules/reader/document-parser.service.ts), documents are decomposed into physical chunks annotated with metadata:
  $$\text{Chunk} = \{\text{id}, \text{paper\_id}, \text{page\_num}, \text{line\_start}, \text{line\_end}, \text{text}, \text{embedding}\}$$
  The synthesizer receives only top-K retrieved chunks and is instructed via system prompt to format every assertion as `[p. X, L. Y-Z]`. The backend verifies that cited ranges exist in the chunk database prior to sending to the client.
- **Deterministic SHA-256 Fallback**: Implemented in [`server/src/modules/ai/gemini-embedding.service.ts`](file:///d:/01_PROJECTS/ACTIVE/S92_Imthiyas_Capstone_Cambium/server/src/modules/ai/gemini-embedding.service.ts). In development, offline CI environments, or during Google API rate limits, the system automatically computes an L2-normalized 768-dimensional float vector from SHA-256 digests. This guarantees that test suites run with 100% determinism at 0 cost.
- **Rejection of Autonomous Agent Frameworks**: Frameworks like AutoGPT or CrewAI encourage multi-step recursive reasoning where agents spawn secondary prompts. In academic peer review, this non-determinism introduces hallucination risks, slow response times (>30s), and token costs. Cambium uses deterministic persona pipelines where prompts are rigorously structured and single-turn grounded.

---

## 6. What Was Rejected & Why
- **Autonomous Multi-Agent Loops**: Rejected due to token cost unpredictability, lack of verification gates, and catastrophic drift in citation accuracy.
- **LangChain / LangGraph**: Rejected due to high abstraction bloat, rapid API deprecations, and unnecessary overhead for structured API calls.

---

## 7. Reconsideration Triggers
Agentic orchestration (e.g., LangGraph or custom state-machine agents) will be introduced if:
1. Cambium introduces multi-step iterative hypothesis generation requiring external web crawling, tool execution, and self-correction cycles.
2. An institutional customer demands custom local LLM fine-tuning and offline Ollama orchestration.
