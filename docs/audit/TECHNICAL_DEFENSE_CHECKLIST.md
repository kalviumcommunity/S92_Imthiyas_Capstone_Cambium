## 1. Top 5 Evaluator Challenge Questions & Scripted Defenses

### Q1: "Your internship curriculum specifies the MERN stack (MongoDB, Express, React, Node). Why did you implement PostgreSQL 16 with pgvector instead of MongoDB?"
> **Senior Staff Response**:
> *"The MERN curriculum teaches core full-stack competencies: RESTful controllers, schema validation, state management, asynchronous persistence, and decoupled microservices. We mapped every MERN paradigm directly to our stack while selecting the optimal database engine for our institutional domain.
> 
> Academic research opportunity discovery handles institutional grant allocations, co-PI eligibility, and compliance protocols where financial integrity and multi-table ACID transactions are non-negotiable. MongoDB's document model lacks native relational integrity constraints and requires multi-document transactions with significant latency penalties.
> 
> Furthermore, Cambium integrates high-dimensional vector embeddings generated by Google Gemini `text-embedding-004` (768 dimensions). In MongoDB, vector search requires MongoDB Atlas paid tiers. By choosing PostgreSQL 16 with the native `pgvector` HNSW extension, we achieved sub-15ms vector similarity queries alongside standard relational queries at **$0 zero cloud infrastructure cost**, fully documented in Architectural Decision Record `ADR-003`."*

### Q2: "How does your system prevent race conditions when two scholars concurrently submit proposals for the same capped grant opportunity?"
> **Senior Staff Response**:
> *"We implemented a multi-layered defense combining Redis Redlock distributed mutual exclusion with PostgreSQL ACID row-level locking.
> 
> When a submission request arrives at `POST /api/grants/submit`, the request passes through our `IdempotencyInterceptor`. If a network retry occurs with the same key, cached results are replayed instantly.
> 
> For the submission itself, `RedlockService.withLock('grant:submit:' + grantId, 5000, async () => { ... })` acquires a distributed lock across Redis instances. If another worker attempts to acquire the lock concurrently, it immediately receives an HTTP `409 ConflictException`. Inside the lock, PostgreSQL executes `SELECT FOR UPDATE` inside a serializable transaction to verify that funding limits have not been breached before decrementing remaining funds."*

### Q3: "How does your file upload implementation protect against arbitrary code execution and directory traversal attacks?"
> **Senior Staff Response**:
> *"Our `UploadService` in `server/src/modules/upload/` enforces defense-in-depth across four distinct security barriers:
> 1. **Path Sanitization**: It invokes `path.basename()` and strips all `../`, `..\`, null bytes `\0`, and control characters using `replace(/[^a-zA-Z0-9._-]/g, '_')`.
> 2. **Extension Whitelisting**: It strictly rejects script or executable extensions (`.exe`, `.sh`, `.bat`, `.php`, `.js`), permitting only valid scholarly artifact formats (`.pdf`, `.docx`, `.bib`, `.csv`, `.tex`).
> 3. **Payload Clamping**: It enforces a strict 50MB ceiling via Multer and throws `PayloadTooLargeException` prior to disk persistence.
> 4. **Storage Isolation & Cryptographic Receipts**: Files are saved with cryptographically random UUID prefixes in an isolated `/server/uploads/artifacts/` directory, and their SHA-256 hash is computed immediately to guarantee tamper detection."*

### Q4: "Explain how your Hybrid Search and Reciprocal Rank Fusion (RRF) algorithm works."
> **Senior Staff Response**:
> *"Standard vector search often misses exact grant identifier numbers or acronyms (e.g. 'NIH R01 CA248123'), while lexical search fails to capture semantic meaning (e.g. matching 'cancer therapeutics' to 'oncology treatments').
> 
> Cambium runs two parallel queries in PostgreSQL:
> 1. A semantic nearest-neighbor query using the pgvector HNSW index with cosine distance operator `<=>`.
> 2. A lexical keyword query using the PostgreSQL GIN index over `to_tsvector('english', title || ' ' || description)`.
> 
> We then fuse both ranked lists using the Reciprocal Rank Fusion formula with constant $k = 60$:
> $$RRF\_Score(d) = \sum_{m \in \{HNSW, GIN\}} \frac{1}{60 + \text{rank}_m(d)}$$
> This yields state-of-the-art search precision without requiring an expensive external Elasticsearch or Pinecone cluster."*
